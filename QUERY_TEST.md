## 3. Test Methodology

### 3.1 Test Execution
- Each prompt was sent via `curl` to `POST /api/chat/stream` with SSE streaming
- Authentication via session cookie
- Provider fixed to `gemini-flash` for all tests
- Timing measured server-side (`elapsed` field in meta response)
- Pipeline time tracked separately (`pipelineMs` field)
- Input/output tokens logged per response

### 3.2 Metrics Captured
- **Total elapsed time**: End-to-end from request to final chunk (server-reported)
- **Pipeline time**: Time spent on intent classification + memory retrieval + embedding + section retrieval (before LLM call)
- **Input tokens**: Total tokens sent to LLM (system prompt + context + user message)
- **Output tokens**: Estimated visible tokens generated by LLM
- **Widget detection**: Whether response contained a ```` ```widget ```` block

### 3.3 Pass/Fail Criteria
- **PASS**: Total elapsed time < 20 seconds
- **FAIL (SLOW)**: Total elapsed time >= 20 seconds

### 4.1 Welcome Screen Scenario

The welcome screen loads on every login/page refresh and must display within **2 seconds**. It runs 3 parallel external calls:

| Component | Source | Target Time |
|-----------|--------|-------------|
| Greeting (name + time of day) | Local | <10ms |
| Weather (city-based) | WeatherAPI.com | <1.5s (timeout) |
| News headlines | NewsAPI.org | <1.5s (timeout) |
| AI personal note (memory-based) | Gemini 2.5 Flash REST | <1.2s (timeout) |
| DB queries (user + profile + memory + messages) | PostgreSQL | <200ms |
| Data snapshot (project/risk counts) | In-memory cache | <10ms |

**Pass Criteria**: Total welcome load < 2 seconds

**Test Results**:

| Scenario | Time | Status |
|----------|------|--------|
| Cold welcome (first load, no cache) | **2.9s** | **SLOW** |
| Cold welcome (weather cached from prior session) | **~1.7s** | OK |
| Cached welcome (within 5-min TTL) | **164-232ms** | OK |
| Subsequent page refreshes | **<250ms** | OK |

**Root Cause of Cold Slowness**: External API calls (WeatherAPI.com ~2.5s, Gemini AI note ~1.5s). These run in parallel, but the slowest determines total time.

**Mitigations Applied**:
1. Weather cache: 10 minutes (weather doesn't change fast)
2. Welcome cache: 5 minutes (full response cached per user)
3. AI note timeout: 1.2s (skips note if Gemini is slow)
4. Weather API timeout: 1.5s (skips weather if API is slow)
5. News API timeout: 1.5s (skips news if API is slow)
6. AI note uses REST API with `thinkingBudget: 0` (no thinking overhead)

**Behavior When Timeouts Hit**:
- Weather timeout → greeting shows without weather info; next load has cached weather
- AI note timeout → greeting shows without personal note; greeting is still warm ("Good evening, Basit!")
- News timeout → greeting shows without news headlines

**Production Note**: After the first cold load, all subsequent loads within 5 minutes return in <250ms. For the demo, open the app once before the presentation to warm all caches.

## 9. Root Cause Analysis

### Issue 1: Sections Never Truncated (25s dashboard)
- **Root Cause**: `sectionRetriever.ts` always included the first matching section in full, regardless of `maxChars` limit. A single section could be 60,000+ characters.
- **Impact**: 18,000+ input tokens sent to LLM for every query, even simple ones like "how many projects?"
- **Fix**: Truncate section body to fit within `maxChars` at the nearest row boundary.

### Issue 2: System Prompt Too Large (3-5s overhead)
- **Root Cause**: `promptService.ts` contained 10,000+ characters of instructions including full HTML/CSS/JS widget examples, duplicate org chart CSS, verbose good/bad examples.
- **Impact**: ~3,000 extra input tokens per request.
- **Fix**: Reduced to 3,500 characters by removing examples (AI already knows HTML), removing duplicate CSS (already in iframe), keeping rules only.

### Issue 3: No Output Token Cap (widgets generate endlessly)
- **Root Cause**: `geminiService.ts` had no `maxOutputTokens` in `generationConfig`. LLM would generate until the model's internal limit.
- **Impact**: Slow generation for simple queries that need short answers.
- **Fix**: Per-intent caps: quick_answer=1024, text=2048, widget=4096.

### Issue 4: Gemini 2.5 Flash Thinking Tokens (widget truncation)
- **Root Cause**: Gemini 2.5 Flash uses internal "thinking" tokens that count against `maxOutputTokens`. With 4096 max output, the model would use ~3,500 for thinking and only ~500 for visible HTML, causing widgets to be truncated mid-generation.
- **Impact**: Dashboard widgets showed partial HTML (stat cards started but no table or charts).
- **Discovery**: REST API response showed `thoughtsTokenCount: 1022` alongside `candidatesTokenCount: 543`.
- **Fix**: For widget intents, bypass the SDK and call Gemini REST API directly with `thinkingConfig: { thinkingBudget: 0 }`. Also filter `thought: true` parts in stream parser to prevent thinking text from being sent to client.

### Issue 5: Intent Classification Slow (6-8s pipeline spikes)
- **Root Cause**: Intent classifier used `gemini-2.5-flash` (with thinking) and had no timeout. Some calls took 6-8 seconds.
- **Impact**: Pipeline time spiked to 8-9s on some requests.
- **Fix**: Added 3-second timeout (falls back to default `detailed_analysis`), added `maxOutputTokens: 256`.

### Issue 6: Response Cache Too Short (30s)
- **Root Cause**: Dedup cache TTL was 30 seconds. Users asking similar questions within minutes got no benefit.
- **Fix**: Extended to 5 minutes. Repeated queries return instantly.

### Issue 7: Scope Embedding Not Cached
- **Root Cause**: Every query called `embedText(scope)` to the Gemini embedding API, adding 1-2s per request even for identical scopes.
- **Fix**: Added 5-minute scope embedding cache keyed by normalized scope text.

## 12. Known Limitations

1. **First request after server restart**: Pipeline takes 8-10s due to cold-start (embedding model loading, Gemini API warm-up). Subsequent requests are 2-3s.
2. **Widget HTML may vary**: Gemini generates slightly different HTML each time. Some dashboard requests may produce simpler widgets depending on available thinking budget.
3. **Large data sections**: If a data section exceeds 15,000 chars, it will be truncated. This may omit some rows from the bottom of the data.
4. **Intent misclassification**: Some prompts may be classified as `conversational` instead of `dashboard` (e.g., "provide me project dashboard" vs "show project status dashboard"). More specific prompts produce better results.
5. **Cache key is message + provider**: Same message with different provider hits different cache entries.
6. **Welcome screen cold load ~2.9s**: First load after server restart exceeds the 2s target due to external API calls (WeatherAPI ~2.5s, Gemini AI note ~1.5s). Timeouts (1.2-1.5s) mitigate this by skipping slow components. Subsequent loads within 5 minutes return in <250ms from cache.

## 13. Recommendations

### For Demo (Immediate)
1. **Warm up the server** before the demo by sending 2-3 test queries
2. **Use specific prompts** like "show project status dashboard" instead of vague "give me dashboard"
3. **Repeat queries** benefit from 5-minute cache -- demo the same dashboard twice to show instant response

### For Production (Post-Demo)
1. **Upgrade SDK** to `@google/generative-ai` v1.x which supports `thinkingConfig` natively, eliminating the REST API workaround
2. **Pre-warm embeddings** on server startup by running a dummy embedding call
3. **Consider Gemini context caching** (Google's cached content API) for system prompts that don't change
4. **Add server-side response time monitoring** with alerts for >15s responses
5. **Pre-generate common dashboards** (project status, sales overview) and cache server-side for instant delivery
